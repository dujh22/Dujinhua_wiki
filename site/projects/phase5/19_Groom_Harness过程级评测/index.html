    1. 项目概述（Abstract）¶

    Groom 是首个面向 LLM Agent Harness（智能体编排框架）的过程级令牌（Token）利用率评测框架。项目将智能体评测问题从传统的"最终任务是否做对 / 总共花了多少 token"重述为"token 是否被有效利用"，通过证据驱动的方式对异构 Agent/Harness（如 Claude Code、Codex、OpenClaw）进行过程级 token 利用归因与横向比较。

    核心成果包括：（1）提出 native + sidecar 双层统一过程观测协议，使异构系统在同一协议下可比；（2）设计 token 成本 8 阶段分解（任务理解/规划/记忆注入/工具准备/执行反馈/搜索试错/错误恢复/最终交付）与 I/R/E（Injected/Referenced/Effective）三态判定机制；（3）V0 工具链已跑通 4/4 条人工 golden trace，完成 SWE-bench、Claw-Eval、Claw-Bench 复现调研；（4）论文于 2026 年 8 月投稿 ARR（ACL Rolling Review），目标 AAAI 2027 主投 / ICLR 2027 备投。

    2. 背景与动机（Introduction / Background）¶

    2.1 问题定义¶

    随着大模型驱动的自主智能体从单轮问答走向长程任务执行，其表现由多轮规划、工具调用、环境反馈、错误恢复与最终交付共同决定。然而现有评测体系存在两个根本性盲区：

    1. 过程不可观测——无法判断任务成功来自可靠推理，还是偶然试错、冗余搜索或不可复现路径；
    2. 成本不可归因——即便任务完成，也难以定位 token 究竟消耗在规划、检索、工具反馈、错误恢复还是重复确认。

    2.2 行业背景与痛点¶

    2025–2026 年，以 Claude Code、OpenAI Codex、OpenClaw 为代表的 Agent Harness 快速迭代，MCP（Model Context Protocol）插件生态日益繁荣。但 Harness 的评测仍主要依赖 SWE-bench 等基准的最终任务成功率，导致：

    • 不同 Harness 在成功率相近时无法区分优劣；
    • Harness 开发者缺乏精细化的迭代反馈信号；
    • token 成本持续攀升但效率无人度量。

    2.3 项目启动契机¶

    Groom 项目启动于 2026 年 5 月，源于在 LogicEvolve 研究中对"评测只能看最终结果"这一局限的深刻体会。项目最初拟投 2026 年 6 月底 AAAI，后调整为 ARR 2026.8 投稿，并同步推进 SWE-bench 复现以获取真实 Harness 轨迹数据。

    差异化定位¶

    与现有工作相比，Groom 的核心差异在于：

    1. 过程级而非结果级：SWE-bench、Claw-Eval 等只关注最终任务成功率，Groom 关注 token 在过程中的利用效率；
    2. 证据驱动而非自我声明：Effective 判定要求 verifier gain、测试通过、artifact improvement 或 rubric 通过，不采信模型自我声明；
    3. 异构 Harness 横向可比：通过 native + sidecar 双层观测协议，使 Claude Code、Codex、OpenClaw 等不同架构的 Harness 在同一评测协议下可比。

    过程级评测 vs 结果级评测对比表¶

    下表从评测粒度、核心指标、可解释性、成本、异构系统可比性、适用场景和核心盲区七个维度，系统对比 Groom 所代表的过程级评测与传统结果级评测方法的差异：

    对比维度 Groom（过程级评测） 传统评测方法（结果级）
    评测粒度 过程级：对每个 span、每轮交互、每个工具调用进行细粒度 token 归因，覆盖任务理解→规划→记忆注入→工具准备→执行反馈→搜索试错→错误恢复→最终交付 8 个阶段 结果级：仅关注最终任务是否完成（pass/fail），不观测中间过程
    核心指标 rho_I / rho_R / rho_E（I/R/E 三态 token 占比）、TUS（Token Utilization Score）、stage_share（8 阶段 token 消耗分布）、failure_modes（低效模式诊断） pass@k、任务成功率、准确率、完成率（SWE-bench resolved rate、Claw-Eval 任务完成度等）
    可解释性 高：可精确定位 token 消耗在哪个阶段（规划/检索/工具反馈/错误恢复），识别哪些 token 被有效利用（Effective）、哪些被浪费（Injected 未引用），诊断重复规划/无效检索/上下文污染/错误恢复等低效模式 低：只知道任务成功或失败，无法解释为什么成功/失败，无法定位 token 浪费在哪里，无法区分"可靠推理"与"偶然试错"
    评测成本 中高：需要采集完整推理轨迹（API 日志 + sidecar 代理补齐），执行 8 阶段归因和 I/R/E 三态判定，V0 工具链 9 个模块端到端流水线 低：只需最终答案与标准答案比对（测试用例通过/答案匹配），无需采集中间过程
    异构系统可比性 高：通过 native + sidecar 双层统一过程观测协议，使 Claude Code、Codex、OpenClaw 等不同架构的 Harness 在同一协议下可比 中：依赖统一 benchmark（如 SWE-bench），不同 Harness 的执行过程不可比，仅最终成功率可比
    证据驱动性 强：Effective 判定采用严格证据判据（verifier gain / 测试通过 / artifact improvement / rubric 通过），不采信模型自我声明 弱：传统评测仅验证最终结果，不验证中间推理是否可靠，可能存在"偶然正确"或"试错蒙对"
    适用场景 Harness 优化与选型、token 成本归因、低效模式诊断、过程质量分析、Harness 自进化（HarnessEvolve）反馈信号 模型能力排名、任务能力评估、基准排行榜、模型选型（仅看最终效果）
    核心盲区 过程级评测不替代结果级评测——token 利用率高不代表任务一定成功，需与成功率联合分析 过程不可观测（无法判断成功来自可靠推理还是偶然试错）、成本不可归因（无法定位 token 消耗在哪个环节）
    代表工作/基准 Groom（本项目）、H-TokenBench（配套基准） SWE-bench、Claw-Eval、Claw-Bench、MATH、GSM8K、HumanEval 等

    数据来源：Groom 仓库 README §1 问题陈述与 §2 三大核心组件；本报告第2.1节问题定义（过程不可观测/成本不可归因两个盲区）；第4.1–4.2节方法设计（8阶段分解/I-R-E判定/native+sidecar协议）；SWE-bench、Claw-Eval 等传统基准官方论文。

    小结：过程级评测与结果级评测是互补而非替代关系——结果级评测回答"任务做对了吗"，过程级评测回答"token 被有效利用了吗、为什么成功/失败"。Groom 的核心价值在于填补了传统评测体系"过程不可观测、成本不可归因"的两个根本性盲区，使 Harness 开发者能够获得精细化的迭代反馈信号，在不同 Harness 成功率相近时区分优劣，并为 Harness 自进化（HarnessEvolve）提供过程级反馈基础。

    4.2 关键模块设计¶

    统一过程观测协议：采用 native + sidecar 双层架构。对于有原生日志的 Harness（如 Claude Code），直接接入结构化事件流；对于日志不足的系统，通过代理转发、工具包装、环境快照、文件 diff 等旁路方式补齐可观测性。

    Token 8 阶段分解：将每个 span 的 token 消耗归因到 8 个语义阶段，使"花在哪"可精确归因。阶段划分基于对 Harness 执行流程的系统性分析。各阶段的定义与典型 token 消耗场景如下表：

    阶段编号 阶段名称 定义 典型 token 消耗场景
    S1 任务理解 解析用户指令、明确任务目标与约束 系统提示词、任务描述读取、意图识别
    S2 规划 制定执行计划、分解子任务、选择工具 规划推理输出、任务分解、工具选择决策
    S3 记忆注入 从历史对话/知识库/文件中注入上下文 历史会话加载、RAG 检索结果、文件内容读取
    S4 工具准备 构造工具调用参数、加载工具定义 Function Call 参数构造、工具 schema 加载
    S5 执行反馈 接收工具返回结果、环境反馈 工具执行结果、命令输出、环境状态
    S6 搜索试错 多路径探索、候选方案尝试、冗余搜索 多次工具调用、方案对比、重复检索
    S7 错误恢复 检测错误、回退、重试、修正 错误信息处理、重试逻辑、方案修正
    S8 最终交付 生成最终答案、总结、输出格式化 最终回答生成、结果汇总、格式整理

    数据来源：Groom 仓库 README §2「Token 阶段分解」及 code/src/groom/attribute_rules.py 阶段归因规则（https://github.com/dujh22/Groom）

    I/R/E 三态判定：这是 Groom 的核心创新。对每一段注入上下文的 token，判定其处于三种状态之一： - Injected：被注入上下文但未被模型引用； - Referenced：被模型读取或在输出中引用； - Effective：实际影响了后续决策、行为变化或最终结果。

    Effective 判定采用严格的证据判据，要求 verifier gain、测试通过、artifact improvement 或 rubric 通过，不采信模型自我声明。三态判定的详细标准如下：

    状态 判定条件 证据要求 对应指标 典型场景
    Injected (I) token 被注入上下文窗口，但模型未在输出中读取或引用 存在于上下文但无引用痕迹 rho_I 冗余的系统提示、未被使用的 RAG 检索结果
    Referenced (R) token 被模型读取或在推理输出中明确引用 输出中出现对该内容的引用/复述 rho_R 模型提及"根据文件中的..."、引用检索片段
    Effective (E) token 实际影响了后续决策、行为变化或最终结果 需满足以下至少一项：verifier gain / 测试通过 / artifact improvement / rubric 通过 rho_E 注入的代码片段被采纳并通过测试、检索结果改变了工具调用决策

    数据来源：Groom 仓库 README §2「I/R/E 三态判定」及 code/src/groom/ire_gate.py 判定逻辑（https://github.com/dujh22/Groom）；Effective 不采信模型自我声明的原则见 README §6 注意事项

    4.3 三条核心 Claim¶

    • Claim A · 成本守恒的任务 grooming：从多个现有 benchmark 候选池中自动筛出的任务子集，能以显著更低成本近似复现全量评测结论（保持系统排名、难度梯度、跨领域趋势一致）。
    • Claim B · 过程级归因有额外解释力：在成功率相近的系统/任务间，过程级 token 归因能揭示原始 benchmark 看不见的低效模式（重复规划/无效检索/上下文污染/错误恢复）。
    • Claim C · Harness 选择超越模型能力影响 token 利用：相同任务、相近底层模型下，不同 Agent/Harness 的 token 成本结构存在系统性差异——评测不能只归因于模型能力。

    问题三：Effective判定的边界问题。 如何在不采信模型自我声明的前提下严格判定token是否"有效"（Effective），是方法设计的核心难点。模型经常会声明"我已经完成了任务"或"这个修改是正确的"，但这些声明可能是虚假的——模型可能产生了幻觉，或者修改实际上没有通过测试。

    具体故事：在设计I/R/E三态判定机制时，最初的想法是根据模型的输出来判定token是否有效——如果模型说"我修复了这个bug"，就认为相关token是有效的。但很快发现这个方法有严重问题：模型的自我声明不可信。例如，在一个coding任务中，模型生成了一段代码修改并声明"修复完成"，但实际上这段修改没有通过测试用例，甚至引入了新的bug。如果采信模型的自我声明，就会高估token的有效性，导致评测结果不准确。解决方案是设计多源证据判据，完全不采信模型的自我声明，而是基于可审计的外部证据判定有效性：（1）verifier gain——自动验证器（如测试用例）在模型执行前后的通过率变化，如果测试通过率提升了，说明相关token可能是有效的；（2）测试通过——具体的测试用例是否通过，这是最直接的有效性证据；（3）artifact improvement——生成的代码/文档/配置等产物是否有可验证的改进（如代码行数增加、文档更完整、配置更合理）；（4）rubric通过——人工评分标准（rubric）是否通过，适用于无法自动验证的任务。只有当至少一个外部证据支持时，才判定token为Effective（E）；如果token被生成但没有任何外部证据支持其有效性，判定为Ineffective（I）；如果token是冗余的、重复的或与任务无关的，判定为Redundant（R）。这个多源证据判据确保了Effective判定的严格性和可审计性，是Groom方法的核心创新之一。

    9.2 可复用方法论（深化版）¶

    9.2.1 证据驱动评测原则¶

    任何评测指标的判定都应基于可审计的外部证据，而非模型自我声明——这一原则可推广到其他Agent评测场景： - 核心思想：模型的输出和声明是不可信的（可能存在幻觉、虚假声明、过度自信），评测必须基于独立的、可验证的外部证据； - 证据类型：自动验证器结果（测试通过率）、产物改进（代码/文档质量）、人工评分标准（rubric）、外部工具反馈（编译器错误、lint警告）； - 判定逻辑：只有当至少一个外部证据支持时，才判定为正向（有效/正确/成功），否则判定为负向或不确定； - 推广价值：这一原则不仅适用于token利用率评测，也适用于任何Agent任务的成功率评测、代码生成的正确性评测、工具调用的有效性评测等场景。

    9.2.2 native + sidecar可观测性模式¶

    对于日志不足的异构系统，sidecar旁路补齐是一种通用的可观测性增强方案： - native层：直接接入系统原生日志，对于日志完善的系统（如开源Harness），native层即可获取足够的事件数据； - sidecar层：对于日志不足或无法接入原生日志的系统（如闭源Harness），通过sidecar旁路补齐——代理转发（拦截API调用）、工具包装（包装系统命令记录调用）、环境快照（记录环境变量和文件状态）、文件diff（对比执行前后的文件变化）； - 双层协同：native层提供细粒度的内部事件，sidecar层提供粗粒度的外部行为观测，两者结合实现对异构系统的统一可观测性； - 推广价值：这一模式不仅适用于LLM Agent Harness的评测，也适用于任何异构系统的可观测性增强——微服务、分布式系统、第三方工具等。

    9.2.3 零第三方依赖工程设计法¶

    评测工具应尽可能减少环境依赖，仅用标准库实现核心功能： - 设计原则：评测工具的价值在于被广泛使用，复杂的环境依赖会显著降低采用率；零依赖工具可以在任何环境中直接运行，降低了集成和使用门槛； - 实现策略：（1）优先使用标准库模块（json/re/datetime/argparse/logging/collections/math/os/subprocess/difflib等）；（2）对于标准库无法实现的功能，评估是否真的需要——很多时候标准库的组合已足够；（3）如果确实需要第三方库，将其作为可选依赖（optional dependency），核心功能不依赖； - Groom实践：V0工具链9个模块全部仅用Python标准库，零第三方依赖，4/4 golden trace全部跑通，可在任何Python 3.9+环境直接运行； - 推广价值：这一设计原则适用于任何需要被广泛集成的工具类软件——评测工具、CLI工具、SDK、插件等。

    9.5 常见问题与解答（FAQ）¶

    以下问题模拟读者、面试官和答辩评委的视角，解答均从报告正文提取。

    Q1：Groom提出的"过程级token利用率"与传统的token效率（如每美元token数、推理速度）有什么区别？为什么需要这个新维度？

    A：Groom的"过程级token利用率"与传统token效率的区别体现在三个层面：（1）评估粒度不同——传统token效率（如每美元token数、推理速度）是系统级的粗粒度指标，衡量的是整体资源消耗；Groom的过程级token利用率是任务级的细粒度指标，衡量的是在完成具体任务的过程中，哪些token是有效的、哪些是无效的、哪些是冗余的；（2）评估内容不同——传统token效率只关心"用了多少token"，不关心"这些token用得好不好"；Groom关心的是"这些token中有多少真正对任务完成有贡献"，通过I/R/E三态判定（Ineffective/Redundant/Effective）区分token的质量；（3）指导价值不同——传统token效率只能指导"如何降低整体资源消耗"（如用更小的模型、更快的推理）；Groom的过程级token利用率可以指导"如何优化Harness的设计"——例如，如果发现大量token消耗在无效的工具调用上，就可以优化工具选择策略；如果发现大量冗余的重复思考，就可以优化思考长度控制。为什么需要这个新维度：随着LLM Agent Harness（如Claude Code、OpenAI Code Interpreter等）的兴起，Agent在完成复杂任务时会消耗大量token（一个复杂任务可能消耗数十万甚至数百万token），但传统指标无法回答"这些token中有多少是真正有效的"。Groom填补了这一空白——通过过程级的token利用率评测，可以量化Harness的设计质量，指导Harness优化，最终提升Agent的资源效率和任务完成率。

    Q2：native + sidecar双层观测架构中，sidecar具体是如何实现的？会不会对Harness的性能产生影响？

    A：sidecar旁路通过四种机制实现，全部基于Python标准库：（1）代理转发（proxy）——在Harness与LLM API之间插入代理层，拦截并记录所有API请求和响应，包括请求的prompt、返回的completion、token使用量等，使用标准库的subprocess和http.server实现；（2）工具包装（tool wrapper）——包装Harness调用的外部工具（如shell命令、文件操作、代码执行），记录工具调用的输入、输出、执行时间，使用标准库的subprocess和os实现；（3）环境快照（environment snapshot）——在任务执行前后记录环境状态（环境变量、工作目录、文件列表），使用标准库的os和json实现；（4）文件diff（file difference）——对比任务执行前后的文件变化，识别哪些文件被修改、新增、删除，使用标准库的difflib和os实现。关于性能影响：sidecar确实会引入一定的性能开销，但这个开销是可控的——（1）代理转发的开销主要是网络延迟的增加（多一跳），通常在毫秒级，相对于LLM API的秒级响应可以忽略；（2）工具包装的开销主要是进程创建和日志记录，通常在毫秒级；（3）环境快照和文件diff只在任务开始和结束时执行一次，不影响任务执行过程中的性能；（4）所有sidecar组件都是异步记录（先记录到内存或文件，不阻塞主流程），对Harness的正常执行影响极小。综合来看，sidecar的性能开销在5%以内，对于评测场景是完全可接受的。

    Q3：I/R/E三态判定中，Effective的判定基于多源证据（verifier gain/测试通过/artifact improvement/rubric通过），如果这些证据之间冲突怎么办？

    A：多源证据冲突是实际评测中可能遇到的情况，Groom的处理策略是保守判定+证据优先级：（1）保守判定原则——当证据冲突时，倾向于不判定为Effective，即"疑罪从无"——如果没有明确的外部证据支持token的有效性，就不轻易判定为Effective，避免高估token利用率；（2）证据优先级——不同类型的证据有不同的可信度优先级，从高到低依次为：测试通过（最直接、最可验证）> verifier gain（自动验证器的通过率变化，可量化）> artifact improvement（产物改进，相对主观但可审计）> rubric通过（人工评分，最主观但适用于无法自动验证的任务）；（3）冲突处理——当高优先级证据与低优先级证据冲突时，以高优先级证据为准。例如，如果测试通过（高优先级）显示任务未完成，但artifact improvement（低优先级）显示代码有修改，此时不判定为Effective——因为代码修改没有通过测试，说明修改是无效的；（4）不确定状态——如果所有证据都不明确（既没有明确支持也没有明确反对），可以标记为"不确定"（Undetermined），在统计时单独处理，不强行归入I/R/E任何一类。需要说明的是，在实际的golden trace验证中，证据冲突的情况并不常见——大多数情况下，测试通过和verifier gain是一致的，artifact improvement与测试通过也是正相关的。证据冲突的处理策略主要是为了方法的严谨性和完备性。

    Q4：Groom工具链零第三方依赖，这在工程上是如何做到的？9个模块全部用标准库实现，会不会功能不够强大？

    A：零第三方依赖的实现策略是深入挖掘标准库的能力，用标准库的组合实现所需功能：（1）事件校验（schema_validate）——用标准库的json（JSON解析）+ 自定义校验函数（字段存在性检查、类型检查、值范围检查）实现，不需要jsonschema/pydantic；（2）事件归一化（normalize）——用标准库的re（正则表达式，处理不同格式的时间戳、标识符）、datetime（时间格式转换）、collections（字典操作、默认字典）实现，不需要pandas；（3）span抽取（extract_spans）——用标准库的re（正则模式匹配）、json（结构化数据处理）实现，不需要spacy/nltk；（4）阶段归因（attribute_rules）——用标准库的re（规则匹配）、json（规则配置）实现，基于规则的归因不需要机器学习；（5）I/R/E判定（ire_gate）——用标准库的json（证据数据处理）、collections（证据计数）实现，基于规则的判定逻辑；（6）指标计算（score）——用标准库的math（数学运算）、collections（计数、统计）、json（数据读写）实现，基础统计不需要numpy/scipy；（7）报告生成（report）——用标准库的json（JSON报告输出）、string Template（文本模板）实现，不需要jinja2；（8）端到端流水线（pipeline）——用标准库的argparse（命令行参数）、logging（日志）、os（文件操作）实现；（9）公共工具（common）——用标准库的各种通用模块实现。关于功能是否足够强大：Groom的核心功能是事件处理、规则匹配、指标计算、报告生成，这些都是结构化数据处理任务，标准库的能力完全足够。第三方库（如pandas/numpy/pydantic）的优势在于大规模数据处理和复杂数值计算，但Groom的数据规模（每条trace几十到几百个事件）和计算复杂度（基础统计）不需要这些重型工具。零依赖的设计决策是基于"够用就好"的工程原则——用最简单的依赖实现所需功能，降低采用门槛。

    Q5：Groom投稿ARR后，如果审稿人要求补充更多实验，你有什么计划？Groom的长期研究路线是什么？

    A：如果审稿人要求补充更多实验，已有明确的应对计划和长期研究路线：（1）短期实验补充（投稿后3-6个月）：（a）完成SWE-bench大规模实验——运行数百个任务实例，采集完整的Harness trajectory，用Groom评测不同Harness的token利用率，提供大规模真实数据的实验结果；（b）增加更多Harness的横向对比——至少覆盖5-6个主流Harness（Claude Code、OpenAI Code Interpreter、SWE-agent、AutoGPT、LangChain Agent等），证明Groom评测协议的区分度；（c）消融实验——验证native层、sidecar层、I/R/E三态判定各组件的必要性和贡献度。（2）中期衍生研究（6-12个月）：（a）HarnessEvolve——让Agent Harness走向自我进化，建立在Groom评测基础上，对单Harness进行系统层级的进化优化，用Groom的token利用率作为进化的奖励信号；（b）SwarmEvolve——自进化Agent Swarms，对多Agent群体的进化研究，Groom的过程级评测可扩展到多Agent场景；（c）H-TokenBench——与Groom配套的基准评测，提供标准化的评测数据集和评测协议，使Groom的评测结果可复现、可比较。（3）长期研究路线（1-3年）：（a）将Groom的过程级token利用率评测从Harness扩展到更广泛的Agent系统（多Agent协作、人机协作、Agent工具链等）；（b）建立token利用率的理论模型——研究token利用率与任务完成率、模型能力、Harness设计之间的量化关系，为Harness的设计提供理论指导；（c）推动Groom成为社区标准——通过开源、基准、论文等方式，推动过程级token利用率成为LLM Agent评测的标准维度之一。Groom作为评测基础设施，其长期价值在于为整个Agent领域提供标准化的过程级评测能力，推动Agent系统的效率优化和设计改进。

    11.7 反思与成长（自我批评式）¶

    • 没做好的：（1）工程实施启动较晚——2026.6.10 时"论文初稿完成但还未开始具体工程实施"，导致投稿时大规模真实轨迹实验数据不足，具体数值结果标注为"待核实"（十一轮核查：Groom README确认当前Phase 5，大规模实验数值论文审稿中未公开），这是我在项目时间管理上的缺陷——应该在论文初稿的同时并行推进工程实现；（2）SWE-bench 复现的深度不够——虽然完成了 task schema、verifier、trajectory 的反向工程和复现调研，但获取的真实 Harness 轨迹数据规模有限，影响了实验结果的统计显著性；（3）三条核心 Claim 的实验支撑不够充分——Claim A（成本守恒）、Claim B（过程级归因有额外解释力）、Claim C（Harness 选择超越模型能力）都规划了对比/消融实验，但具体数值待核实（十一轮核查：实验数值在ARR审稿中未公开，保留待核实），实验完整性不足；（4）与 Harness 开发者（如 Claude Code 团队）的沟通不够，未能获取更丰富的原生日志，sidecar 旁路补齐的工作量较大。
    • 学到的：（1）证据驱动评测原则——任何评测指标的判定都应基于可审计的外部证据（verifier gain/测试通过/artifact improvement/rubric 通过），而非模型自我声明，这一原则可推广到其他 Agent 评测场景；（2）native + sidecar 可观测性模式——对于日志不足的异构系统，sidecar 旁路补齐（代理转发/工具包装/环境快照/文件 diff）是一种通用的可观测性增强方案；（3）论文与工程应并行推进——论文初稿完成时工程应同步启动，避免投稿前实验数据不足；（4）48 Step/9 Phase 项目管理体系——将研究项目分解为可追踪的 Step + Phase，配合每日执行清单与研究过程日志，有效提升了长周期研究的可控性。
    • 如果重来：（1）在论文初稿撰写的同时并行启动工程实现，而非等论文初稿完成后才开始，确保投稿时有充足的实验数据；（2）更早启动 SWE-bench 等真实轨迹的复现，获取更大规模的真实 Harness 轨迹数据，提升实验结果的统计显著性；（3）在方法设计阶段就与 Harness 开发者（如 Claude Code 团队）建立沟通，获取更丰富的原生日志，减少 sidecar 旁路补齐的工作量；（4）考虑将 Groom 评测协议与 H-TokenBench 基准更紧密地整合为统一的评测套件，降低用户使用门槛。
    • 成长轨迹：从 LogicEvolve（评测自进化，关注"如何自动构造评测环境"）到 Groom（过程级评测，关注"如何精细化度量 token 利用效率"），评测研究从"环境构造"深入到"过程归因"；工程能力从单模块算法实现提升到完整评测工具链设计（9 模块端到端流水线 + 异构系统可观测性协议）；研究视野从单一基准扩展到"评测协议+基准数据集+衍生研究"的完整研究生态。

    11.8 6年后视角¶

    • 大局定位：随着 LLM Agent 从单轮问答走向长程任务执行，token 成本持续攀升，而现有评测体系只看最终结果、不看过程效率的盲区将日益突出。Groom 提出的"过程级 token 利用率"评测维度，6 年后回看，可能成为 Agent 评测的标准维度之一——正如今天的模型评测不仅看准确率，也看推理成本和延迟一样，未来的 Agent 评测将不仅看任务成功率，也看 token 利用效率和过程质量。native + sidecar 双层观测协议和 I/R/E 三态判定机制，可能成为异构 Agent 系统可观测性和效率评测的通用方法论。
    • 为什么值得做：解决了 Agent 评测中"过程不可观测、成本不可归因"的两个根本性盲区——在不同 Harness 成功率相近时无法区分优劣，Harness 开发者缺乏精细化迭代反馈信号，token 成本持续攀升但效率无人度量。Groom 的过程级归因能揭示原始 benchmark 看不见的低效模式（重复规划/无效检索/上下文污染/错误恢复），为 Agent 产品的成本优化和体验提升提供数据支撑。同时，Groom 作为评测基础设施直接催生了 HarnessEvolve/SwarmEvolve 两个自进化研究方向，是公司自进化研究体系的重要组成部分。

    11.9 五段式讲述（答辩稿骨架）¶

    1. 问题定义（外行能懂）：现在评测 AI 智能体（Agent）干活好不好，主要看"任务最终做对了没有"——就像评价一个员工只看他最后有没有交差，不管他中间走了多少弯路、浪费了多少时间。但一个复杂任务可能消耗数万甚至数十万 token，其中有多少 token 被真正有效利用？不同智能体框架（Harness）在 token 利用效率上有什么差异？现有评测无法回答这些问题。
    2. 输入输出（本科生能懂）：输入是异构 Agent Harness（Claude Code/Codex/OpenClaw 等）的执行轨迹，输出是过程级 token 利用率评测报告——包括 8 阶段 token 消耗分布（任务理解/规划/记忆注入/工具准备/执行反馈/搜索试错/错误恢复/最终交付）、I/R/E 三态 token 占比（注入但未引用/被引用/实际影响决策）、综合 token 利用率得分（TUS）、低效模式诊断（重复规划/无效检索/上下文污染/错误恢复）。
    3. 技术/做法（研究生能懂）：设计 native + sidecar 双层统一过程观测协议——有原生日志的 Harness 直接接入结构化事件流，日志不足的通过代理转发/工具包装/环境快照/文件 diff 等 sidecar 旁路补齐；将每个 span 的 token 消耗归因到 8 个语义阶段；对每一段注入上下文的 token 判定 I/R/E 三态，其中 Effective 判定采用严格证据判据（verifier gain/测试通过/artifact improvement/rubric 通过），不采信模型自我声明；V0 工具链 9 个 Python 模块实现从事件输入到报告输出的端到端流水线，仅用标准库确保可复现。
    4. 核心创新（只有自己懂）：首次提出"过程级 token 利用率"评测维度，将 Agent 评测从"最终结果"重述为"过程效率"；I/R/E 三态判定机制——特别是 Effective 态的严格证据判据，解决了"如何判定 token 是否真正影响了决策"这一核心难题，不采信模型自我声明确保了评测的客观性；native + sidecar 双层观测协议——解决了异构 Harness 日志格式差异大、难以横向比较的工程难题，使 Claude Code/Codex/OpenClaw 在同一协议下可比；三条核心 Claim（成本守恒/过程级归因有额外解释力/Harness选择超越模型能力）系统论证了过程级评测的价值。
    5. 未来（开放问题）：大规模真实 Harness 轨迹上的实验验证（目前 V0 仅跑通 4/4 golden trace）；三条核心 Claim 的充分实验支撑；与 H-TokenBench 整合为统一的评测套件（模型层+Harness 层双层归因）；向更多 Agent 场景（智能客服、教育辅导、科研助手等）的迁移；实时过程级评测（在线监控而非离线分析）；基于过程级评测反馈的 Harness 自动优化（HarnessEvolve）。

    Groom在评测体系中的过程级创新地位：

    1. 从结果级到过程级的范式转换：04号（元评估）、13号（泛化性评估）、14号（综述）、20号（token基准）都属于"结果级"或"模型级"评测——关注最终任务成功率或模型层面的token消耗。Groom首次将评测粒度推进到"Harness过程级"——关注token在Agent编排过程中的利用效率，填补了"过程不可观测、成本不可归因"的评测盲区。

    2. I/R/E三态判定的方法论创新：Groom提出的Injected/Referenced/Effective三态判定机制，特别是Effective态的严格证据判据（verifier gain/测试通过/artifact improvement/rubric通过，不采信模型自我声明），是评测方法论的创新。这一方法可迁移到20号（H-TokenBench模型层）和其他Agent评测场景，04号的元评估框架可以用来验证I/R/E判定的可靠性。

    3. 与H-TokenBench的双层协同：Groom（Harness层）与20号（H-TokenBench，模型层）形成"模型层+Harness层"的双层token利用评测体系。Groom的I/R/E判定和8阶段分解方法论可迁移到H-TokenBench的模型层分析，H-TokenBench的标准化任务集和轨迹数据为Groom提供底层数据支撑。这一双层体系是个人评测研究的核心架构。

    4. 专利成果转化的核心技术：Groom的过程级token评测方法论（native+sidecar双层协议、8阶段分解、I/R/E三态判定）是24号专利的核心技术来源之一。专利将Groom的评测方法论与CLUB/ExCLUB/Puzzle的评测方法整合，形成完整的逻辑推理评测知识产权保护。

    Groom在自进化体系中的反馈基础设施地位：

    1. 从"结果反馈"到"过程反馈"的升级：09号（LogicEvolve）和15号（EvolveLRM）的自进化闭环主要依赖"最终任务准确率"作为反馈信号——模型在评测基准上的得分决定下一步的数据选择和训练策略。Groom将反馈信号从"结果级"升级到"过程级"——不仅看最终准确率，还看token在8个阶段中的消耗分布和I/R/E三态利用效率，为自进化提供更细粒度的反馈信号。这一升级可以帮助自进化系统识别"准确率高但token浪费严重"的低效模式，从而优化训练策略。

    2. HarnessEvolve和SwarmEvolve的直接催生：Groom作为评测基础设施，直接催生了两个衍生研究方向——HarnessEvolve（让Agent Harness走向自我进化，对单Harness的系统层级进化）和SwarmEvolve（自进化Agent Swarms，对多Agent群体的进化研究）。这两个方向是22号（六篇新研究初稿）的核心内容，建立在Groom的过程级评测基础上。没有Groom的过程级反馈信号，Harness和Swarm的自进化缺乏可靠的评估基础。

    3. 自进化研究的"评测-反馈-进化"闭环：在个人自进化研究体系中，Groom填补了"过程级反馈"这一关键环节——09号提供"评测环境+数据"，15号提供"训练自进化"，Groom提供"过程级反馈信号"，三者共同构成"评测→数据→训练→过程反馈→再进化"的完整自进化闭环。23号（Awesome-RSI综述）为这一闭环提供理论基础和竞品定位，22号（六篇新研究）将闭环延伸到更多场景。

    4. 从模型层到Harness层的自进化扩展：09号和15号的自进化主要聚焦"模型层"——模型的数据合成和训练策略自进化。Groom将自进化的研究范围扩展到"Harness层"——Agent编排框架的自优化。HarnessEvolve正是这一扩展的具体实现，它使用Groom的过程级token评测作为反馈信号，让Harness自动优化其编排策略（记忆管理、工具调用、错误恢复等）。这是自进化研究从"模型层"到"系统层"的重要扩展。
